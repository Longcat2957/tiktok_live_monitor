# 프론트엔드 개선 계획 및 검증 결과

## 범위

현재 단일 계정 모니터와 TikTok 색상·m3-svelte 컴포넌트를 유지하면서 요청 복구, 댓글 읽기, 설정, 접근성과 화면 갱신을 개선한다. 댓글·계정·설정의 서버 영구 저장은 추가하지 않는다. 브라우저에는 테마와 글자 배율만 저장한다.

## 계획과 구현

- [x] **요청 완료 보장:** 변경 요청 15초, 읽기 요청 5초 제한. 응답 유실 시 변경을 자동 재전송하지 않고 `/health`의 세션과 `pending_commands`를 조회한다. 결과 미확정 중 중복 변경을 막고 설정창은 닫을 수 있게 한다.
- [x] **상태별 안내:** 서버 연결, 방송 연결·시작 대기, 첫 댓글 대기, 일시정지, 종료, 수신 오류를 구분한다. 기존 댓글은 상태 변화만으로 지우지 않는다.
- [x] **부가정보 허용:** 잘못된 사진 URL·배지는 제외하고 유효한 작성자와 댓글·활동을 유지한다. 배지는 종류별 하나, 최대 두 개다. 필수 데이터 검증과 plain text 표시는 유지한다.
- [x] **글자 배율:** 현재 배율 표시, 20–200% 범위 5% 조절, 브라우저 저장·복원과 손상된 저장값 복구를 구현한다.
- [x] **이전 댓글 읽기:** 위로 이동하면 자동 따라가기를 멈추고 읽던 첫 항목과 픽셀 위치를 보존한다. 새 항목 수와 최신 이동 버튼을 제공한다. 보관 범위 밖으로 삭제된 항목은 안내하며 새 세션에서는 최신 따라가기로 초기화한다.
- [x] **활동 알림:** 선물·팔로우·공유·구독을 댓글보다 작은 1–2줄로 표시한다. 긴 알림은 말줄임하고 전체 텍스트와 title을 유지한다.
- [x] **설정 구분:** 기본에는 목록 보관 수와 데모 간격, 접힌 고급 설정에는 큐·로그와 실제 방송 재연결 간격을 둔다. 목록 보관 수가 댓글과 활동의 합계임을 설명한다. 접힌 필드가 잘못되면 자동으로 펼쳐 초점을 이동한다.
- [x] **첫 화면 테마:** 계정을 연결하기 전에도 동일한 테마 버튼을 사용한다.
- [x] **구조·접근성:** HTTP 요청과 상태 표현을 작은 공통 모듈로 분리한다. 시작·종료·설정창 전환의 포커스를 보존한다. 목록에서 방향키·Page Up/Down·Home/End를 지원하며 수신 알림은 초당 한 번 개수로 요약한다.
- [x] **측정 후 성능 개선:** 재현 가능한 벤치마크로 큰 보관 수의 갱신 지연을 확인하고, `requestAnimationFrame`으로 댓글 반영을 프레임당 한 번으로 묶었다. 대기 배치도 보관 수 이내로 제한하고 세션 변경 시 즉시 폐기한다.

## 검증

- Backend: pytest 40개, mypy, ruff(app/tests).
- Frontend: strict TypeScript/Svelte check 오류·경고 0개, 단위 테스트 37개, static production build.
- Browser: E2E 21개. 선택·설정·재연결·다른 화면의 상태 변경, 응답 유실/시간 초과, 테마·배율 저장, 부가정보, 1,000건 순서·보관 상한을 검사한다.
- 읽기 모드: 보관 목록 앞부분 삭제와 글자 확대 후 기준 항목의 위치 오차 ≤1px, 기준 항목 퇴출 안내, 새 항목 수 상한, 키보드/버튼 최신 복귀, 세션 변경 시 대기 프레임 폐기를 검사한다.
- 접근성: 1080×1920, 720×1280 모니터 및 390/320px 너비, 키보드 설정창 개폐·포커스 복귀, 접힌 입력 오류 공개를 검사한다. 스크린 리더 낭독 자체는 실제 보조기기에서 별도 확인해야 한다.

## 성능 측정

실행: `cd frontend && pnpm build && pnpm benchmark ../docs/frontend-benchmark-local.json`.
Python 가상환경과 Playwright Chromium을 사용한다. 스크립트가 임시 localhost 서버를 시작·종료하며 TikTok 연결 없이 브라우저 WebSocket에 샘플을 주입한다. 각 회차의 마지막 보관 항목 ID와 순서를 검사한다. 메모리 무제한 증가 방지는 목록과 대기 배치 상한으로 보장하며, 이 짧은 측정은 장시간 힙 측정을 대신하지 않는다.

환경: Linux x64, Intel i9-14900HX, Chromium 153.0.8010.12, 1080×1920, CDP CPU 4배 지연. 보관 수별 1,000건을 목표 500건/초로 보내고 3회 측정했다. 실제 주입 간격에는 Node/CDP 처리 시간이 포함된다. 아래 값은 3회 결과의 중앙값이다.

| 보관 수 | 개선 전 프레임 간격 p95 | 개선 후 프레임 간격 p95 | 마지막 항목 표시까지 전 → 후 |
| --- | --- | --- | --- |
| 30 | 16.8ms | 16.8ms | 2.23초 → 2.26초 |
| 1,000 | 116.7ms | 33.4ms | 5.18초 → 2.30초 |

원본: [개선 전](frontend-benchmark-before.json), [개선 후](frontend-benchmark-after.json). 기본 보관 수의 한 회차에 64ms long task가 1회 기록되었으며 나머지 회차에는 없었다. 기본 크기는 안정적으로 유지하고, 1,000개 보관의 높은 수신량에서는 약 30fps 수준의 프레임 간격으로 개선했다. DOM 가상화나 별도 상태 라이브러리는 추가하지 않았다.

## 장비 검증의 범위

위 수치는 로컬 CPU 지연 실험이며 Raspberry Pi 성능 수치가 아니다. Pi의 Chromium은 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium pnpm benchmark ...`로 지정해 같은 시나리오를 실행할 수 있다. 실제 Pi의 장시간 메모리·온도·터치 조작, 실방송 수신은 이번 로컬 검증에 포함하지 않았다. 기능 구현과 mock 검증 완료 여부와 이 장비 검증 범위는 구분한다.
